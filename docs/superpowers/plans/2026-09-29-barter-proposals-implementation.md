# 第二阶段：投物箱与协商实施计划

> 按 superpowers:subagent-driven-development 逐任务执行：每项先观察失败测试，再做最小实现、测试、提交，并由新的审查代理独立检查。七项按顺序，不能并行修改依赖模块。

**目标：** 两名普通用户通过已上架物品形成可协商的结构化交换方案；接受时独占占用所有物品 72 小时。本阶段无订单、资金流水、物流或聊天。

**基线：** `fcf72d8`；开发分支 `codex/phase2-proposals`；第一阶段 PR 未合并前，第二阶段 PR 以第一阶段分支为基线。

**规格：** `docs/superpowers/specs/2026-09-29-barter-proposals-design.md`，并遵守第一阶段总体设计及 `AGENTS.md`。

## Global Constraints

- 用户端和运营端共用 NestJS API 和 `@barter/contracts` Zod 类型；权限、物品所有权、提案参与身份只在服务端判定。运营人员不能冒充用户出价、接受、拒绝或取消。
- 发起方提供自己的 1～5 件已上架物品，接收方提供自己的 1 件已上架目标物品；一份方案总计 2～6 件。只有当前回应方可修改；双方只能修改自己侧物品，但都可修改差价及运费条款；每次出价生成不可修改方案版本并使旧版确认失效。
- 差价为 0～20000 整数分，付款方向明确；零差价时付款方为 NONE。COURIER 模式保存双方各自承担的非负整数运费估计；IN_PERSON 模式运费均为零。这里没有支付和资金流水。
- 所有提案写命令要求 `Idempotency-Key`；创建之外均要求 `expectedVersion`。相同键同内容重放原结果，不同内容返回明确 409。版本冲突同样返回明确 409。API 时间为 UTC ISO 8601。
- 待回复提案自最近一次出价起 7 天失效。接受须在一个 PostgreSQL 事务内重新验证版本、期限、所有物品仍上架且未占用，独占占用 72 小时，写入状态与审计。任何冲突导致整笔 409 且无部分占用。双方可取消已确认方案释放占用；到期自动释放。定时任务与请求时期限检查共用状态转换服务。
- 未确认的不同提案可包含同一物品；同一物品同时只能被一个未到期的已确认方案占用。已占用物品公开可查看但不可投。
- 不实现订单、真实支付、物流、聊天、售后、现金购买或独立运营小程序。生产身份和存储适配器仍不可使用测试替身。
- 保留第一阶段行为；测试、构建及 CI 均须继续通过。

## Task 1: 设计、契约、数据模型与双用户测试身份

**交付：** 完成本计划对应的设计文档；在共享契约定义公开物品视图、提案状态、方案版本、命令模式、错误码；新增 Prisma 提案/不可变版本/方案物品/独占占用模型、迁移；测试专用身份提供器支持两个独立用户，不改变生产微信接入。

**测试优先：** 先写契约验证测试和身份提供器双用户测试并确认失败，再实现；迁移用 PostgreSQL 实跑并检查约束。提案版本存储必须可独立重建历史方案；占用以数据库唯一约束保护。

**建议提交：** `feat: define proposal contracts and persistence`

## Task 2: 公开物品发现

**交付：** 公开 `GET /api/items` 稳定游标列表和 `GET /api/items/:id` 详情，只返回 ACTIVE 及安全字段；默认每页 20，明确 nextCursor；已占用仍可见但 `availableForProposal=false`。Taro 新增找换入口、列表、公开详情。

**测试优先：** 非公开物品不可枚举/读取，私有字段不泄漏，分页稳定，已占用标识；先红后绿，API 与前端各有覆盖。

**建议提交：** `feat: add public item discovery`

## Task 3: 创建、列表与详情

**交付：** `POST /api/proposals`、`GET /api/me/proposals`（发出/收到）、`GET /api/proposals/:id`；参与者才能看详情。创建校验双方不同、目标归属、自己 1～5 件、状态/占用、金额、付款方、配送、幂等；创建后轮到接收方、7 天待回复期限。

**测试优先：** 跨用户越权、非自有物品、重复物品、非法数量/金额/运费、重复键内容一致与不一致、审计失败回滚。

**建议提交：** `feat: create and query exchange proposals`

**任务 3 实施记录（2026-09-29）：** 已交付创建、发出/收到列表与参与者详情；8 项 API 集成测试先红后绿，覆盖完整快照、权限、数量/金额/配送、物品可用性、并发幂等和审计回滚。根 `npm run verify` 通过。协商命令和自动到期仍按任务 4～5 交付。

## Task 4: 协商状态机

**交付：** `POST /api/proposals/:id/counter`、`accept`、`reject`、`cancel`；当前回应方才能 counter/accept/reject；发起方只能改自己的多件物品，接收方只能替换自己的目标物品；都可改条款。counter 生成新版本、轮到对方、重置 7 天期限；每条命令版本检查与幂等。拒绝结束待回复提案；双方可取消待回复或已确认提案；审计与状态同事务。接受先接入状态机，实际占用由任务 5 完成，合并前不能暴露无占用的确认状态。

**测试优先：** 双方同时修改、错轮次、越侧修改、陈旧版本、重复命令、审计回滚、版本历史不可变。

**建议提交：** `feat: add proposal negotiation state machine`

**任务 4 实施记录（2026-09-29）：** 四个命令入口已接入共享状态转换服务；counter/reject/cancel 成功返回 200，接受在任务 5 原子占用完成前固定受控返回 409 PROPOSAL_INVALID_STATE。行锁保证并发版本/轮次检查，完整不可变报价、状态、幂等及前后审计同事务；取消已确认提案会原子释放占用。新增 6 项 API 集成测试先红后绿，覆盖双方修改、越侧权限、幂等重放、终止状态、审计回滚和拒绝无占用确认。期限越界命令已拒绝，到期转换及定时清理由任务 5 实现。根 `npm run verify` 全部通过（API 90、运营端 18、小程序 35、契约 23、根脚本 4 项测试）。

## Task 5: 原子占用和期限处理

**交付：** 完成接受时 2～6 件的独占占用；竞争同一物品仅一份成功；7 天待回复到期、72 小时确认占用到期，取消/到期释放；定时任务调用与请求路径相同状态转换逻辑。过期命令不得成功，事务确保状态、占用、审计原子性。

**测试优先：** 两提案争抢同物品、并发接受、单件失败整单回滚、审计失败回滚、到期释放、释放后重新可投、延迟定时任务下请求时校验。

**建议提交：** `feat: reserve proposal items atomically`

**任务 5 实施记录（2026-09-29）：** 已启用事务内全量接受占用（2～6 件，72 小时），物品顺序加锁后重验归属/状态/占用；竞争失败返回 409 且无部分写入。共享到期转换支持 7 天待回复、72 小时确认、参与者读取、新命令及 60 秒周期扫描，自动到期与释放同事务写系统审计。过期命令先回滚自身再独立提交到期；旧过期占用先审计清理再重试接受。测试覆盖竞争、同键并发重放、最大六件、不可用物品、接受/取消/到期审计回滚、已过期确认的取消、公开可投恢复和过期占用重用。
