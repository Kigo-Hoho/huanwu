## 目标、约束与不包含内容

两名普通用户将已经确认的交换方案转换为订单，通过保证金和差价的测试支付、双方快递或面交、双方验收，完成可运行、可追溯的履约与结算闭环。原有发布、审核、协商和未转换提案的期限规则必须保持兼容。

本阶段没有获得真实支付商户或物流服务接入资料，采用完整业务接口加显式测试适配器。测试产生的支付、退款、结算和物流结果必须明确标记为模拟，不能称为真实资金交易。生产配置必须拒绝模拟适配器；未实现或未配置真实适配器时，相关能力明确不可用，不能返回伪造的生产成功结果。真实适配器需根据实际合作方接口另行实现与验收，不能把通用接口壳当作已经接入。

继续遵守：整数分、CNY 币种、UTC ISO 8601、服务端身份与资源权限、稳定幂等键、版本冲突、状态与不可删除审计同事务。运营账号不能兼任订单参与者执行用户命令。

所有订单用户写接口除要求 CUSTOMER 外，还明确拒绝携带任一运营角色的会话；即使错误配置同时授予 CUSTOMER 和运营角色，也不能绕过身份隔离。运营只能使用独立只读接口。

本阶段不包含售后证据、责任裁决、部分退款、保证金罚扣、退货物流、账号冻结、运营修改费用或期限、真实资金上线、聊天、纯现金购买及独立运营端小程序。异常订单保留占用并进入待处理状态，供第四阶段接管；不是任意运营人员可直接退款、解锁或结算的后门。

## 已确认的测试规则

每个订单保存完整规则快照和规则版本；后续配置变化不能修改既有订单。

| 规则 | 测试默认值 | 起算点或含义 |
| --- | --- | --- |
| 保证金 | 每人 1000 分 | 双方各自承担；本阶段不罚扣 |
| 平台服务费 | 0 分 | 不新增收费入口或非零收费规则 |
| 差价 | 沿用已确认方案的 0～20000 分 | 付款方向不可重协商，零差价无差价支付义务 |
| 支付期限 | 24 小时 | 订单满足必要收货资料后进入待支付时起算 |
| 发货／面交期限 | 72 小时 | 全部必要资金确认成功后，双方共用一个截止时间 |
| 验收期限 | 每方 72 小时 | 该方收到对方物品的可信签收／交接记录后起算 |

快递订单另有资料准备期限：建单后 24 小时内双方完成必要收货资料，超时走无发货取消路径。它与支付期限分开，避免未提供地址时催促支付。面交不要求快递地址，建单直接进入待支付。资料期限是本书面规格对真实发货所需前置条件的细化，需随本文件一起审阅。

验收逾期不等于用户同意，不自动确认收货或结算。发货截止时未完成双方可信揽收／面交交接，或出现物流异常，进入待处理状态；没有任意自动解锁规则。测试用可注入时钟推进期限，不能把客户端时间作为裁决依据。这些数值仅为开发验收参数，不能据此宣称正式上线的保证金或收费规则已定。

## 模块职责

- 订单模块：订单创建、参与人、不可变交易快照、双向履约进度、取消协商、版本和状态转换。
- 占用模块：统一表达提案租约与订单占用，排序锁定和原子交接。物品公开查询和全部提案命令通过同一可用性规则判断，不继续复制原有仅比较 `expiresAt` 的逻辑。
- 提案模块：提供事务内转换接口，核验确认版本和有效占用并标记 CONVERTED；原有接受、取消、到期仍由自身服务处理。
- 支付模块：付款义务、唯一支付意图、可信事件、退款／结算任务、不可变资金记录及支付适配器。不提供可自由使用的平台余额。
- 物流模块：每方一个包裹的运单、可信揽收／签收事件、事件去重和查询适配器。发起方的 1～5 件物品必须全部归入同一发货任务，不能只发其中一部分后宣称完成。
- 任务模块：数据库中的到期扫描、外部命令投递和结果核对。定时处理与请求检查调用同一业务转换服务。
- 现有身份、共享契约、审计和前端模块：扩展已有明确接口，保持普通用户与运营身份隔离。

订单服务可以通过公开的事务接口调用提案和占用模块，不直接依赖提案服务的私有方法。所有事务接口使用同一个 Prisma transaction client；任何服务都不能自行开一个独立事务来声称完成原子交接。

## 建单与占用交接

任一参与者在未到期的 CONFIRMED 提案详情页执行“生成交换订单”，携带 `expectedVersion` 和 `Idempotency-Key`。不在第二阶段接受接口中悄悄自动建单，保留既有验收行为。已转换提案显示订单入口，不再提供提案取消或修改操作。

在一个 PostgreSQL 事务内：

1. 锁定并重读提案，核验 CUSTOMER、参与者、当前修订号、CONFIRMED、当前报价及占用期限。
2. 按物品 ID 排序锁定全部 2～6 件物品，锁后重新核验期限、所有权、ACTIVE 状态及完整占用。
3. 每条占用的 proposalId、proposalVersionId、物品集合和期限必须与当前方案完全对应；缺一条、多一条或归属不符均失败，不补造占用。
4. 为该提案创建唯一订单，复制确认版本和全部物品快照、双方身份、条款、测试／真实集成标识和规则版本。
5. 原位将全部占用改为订单占用，提案改为 CONVERTED 并增加修订号，保存关联 orderId。订单占用没有提案租约到期时间。
6. 写入订单创建和提案转换审计、原始幂等成功响应，一起提交。

禁止先删除提案占用、提交，再异步建单。任一校验或审计失败整笔回滚，返回明确冲突，原提案和占用不变。

数据库用 `Order.proposalId` 唯一约束保证一份提案只对应一个订单。相同 actor／command／key 同内容重放原结果；不同内容返回 IDEMPOTENCY_CONFLICT。另一参与者用不同键重试转换时不能创建第二笔：若已经 CONVERTED，返回包含已有关联订单标识的 PROPOSAL_ALREADY_CONVERTED 冲突，客户端刷新并进入该订单。原成功键即使在转换或终态后仍可重放。

过期转换请求先拒绝自身事务，再调用共同的提案到期转换，不能让业务错误回滚必要的审计清理。CONVERTED 提案永不被原提案到期扫描释放。转换后的所有后续操作走订单命令，不允许提案取消接口控制订单。

### 占用与完成后物品

沿用一物一占用行的数据库唯一性，并将 ItemReservation 扩展为互斥的两种所有者：

- 提案租约：proposalId、proposalVersionId、expiresAt 非空，orderId 为空。
- 订单占用：orderId 非空，proposalId、proposalVersionId、expiresAt 为空；历史来源由订单快照追溯。

数据库 CHECK 保证恰好一种所有者，相关外键采用 Restrict。迁移保留所有既有提案租约，不丢失当前数据。

公开物品列表仍只展示 ACTIVE，订单占用无论是否已经超过原来的 72 小时都显示 `availableForProposal=false`。创建、修改、接受提案同样拒绝订单占用。异常、取消退款中、结算中的订单仍占用物品。

成功完成时，在状态、审计同一事务内把全部原物品改为 INACTIVE、增加物品修订并释放占用；不得把原物品自动重新上架，也不把原发布记录的 ownerId 转给新持有人。新持有人以后重新发布必须创建新物品并正常审核。安全取消后，未发生交接的原物品保留原所有权和 ACTIVE 状态，并释放订单占用。

## 订单状态与双方进度

订单总体状态表示当前阶段，双方单独保存资金、发货、收货与验收进度，不能用单个布尔值替代双向履约。

| 状态 | 进入条件 | 允许的主要动作 |
| --- | --- | --- |
| AWAITING_DETAILS | 快递建单成功 | 各方维护自己的收货资料、提出取消 |
| AWAITING_PAYMENT | 必要资料齐全或面交建单 | 各方发起自己的付款、提出取消 |
| AWAITING_FULFILLMENT | 两份保证金及必要差价均可信确认 | 各方提交自己的运单或面交交接确认 |
| IN_TRANSIT | 快递双方运单均有可信揽收 | 查询物流，签收后各方可验收自己的来件 |
| AWAITING_ACCEPTANCE | 双方来件均已可信签收／面交交接完成 | 各自确认验收或标记存在异议 |
| SETTLING | 双方均已验收，无异议或有效取消请求 | 仅后台执行差价结算和保证金返还 |
| COMPLETED | 全部必要外部结算与返还确认成功 | 只读历史，原物品下架并释放占用 |
| CANCEL_PENDING | 合法双方取消或付款／资料超时，且无交接风险 | 关闭未决支付、核对结果、全额退款；不允许发货 |
| CANCELLED | 支付意图关闭、退款完成且未发生交接 | 只读历史，释放占用 |
| ON_HOLD | 物流、逾期、验收异议或无法判定的资金异常 | 只读与异常说明，禁止新发货、验收、结算和自动解锁 |

每次成功业务转换增加订单 `version`。外部通知不使用客户的 expectedVersion，但必须持锁重读状态并按可信事件去重。客户端写命令需要 expectedVersion；冲突时显示现版并要求用户重新确认，不能静默覆盖。

期限采用 `服务端当前时间 >= 截止时间` 的闭区间到期规则，等待锁后必须再检查，不能沿用入请求时的旧时间。成功命令重放先核验身份、参与权限和原请求哈希，返回原成功结果，不因后来到期重复执行业务；新命令才进入共同期限转换。资料、支付、履约和验收期限仅在其对应阶段生效，CANCEL_PENDING／SETTLING 不因旧期限到期被错误推进，COMPLETED／CANCELLED 不再运行业务到期转换。

快递中只有一方被揽收时总体状态仍可为 AWAITING_FULFILLMENT，详情必须显示该方的独立进度，且取消保护已生效。一方先收到物品时可先验收自己的来件，不能验收自己的去件或对方来件；另一方到达后才满足双方结算条件。

ON_HOLD 保存 holdReason、前序阶段、触发时间及尚未完成的义务。第三阶段不提供任意“解除异常”按钮或跳转到完成的通用状态修改接口。第四阶段的恢复／退货／资金处置必须有独立权限和状态机，不得直接改数据库绕过本阶段记录。

## 收货资料与隐私

快递订单必须有双方各自提供的收件人、电话和地区／详细地址。用户只能维护自己一侧，全部必要资料冻结后才进入待支付；付款开始后不能悄悄修改对方已经依据其准备的地址。

- 自己可读取自己保存的资料；对方只有在资金条件满足后才能读取其发货所需的收件资料。
- 非参与者统一 404；运营订单查询默认脱敏，不显示完整电话和地址，不提供第三阶段完整地址导出或查询特权。
- 地址和电话在数据库中加密保存，密钥从运行环境注入，使用随机 nonce 的 authenticated encryption；测试使用临时测试密钥。生产缺少密钥明确拒绝，不能明文回退。
- 审计只记录资料版本、变更类型和脱敏摘要，不写完整地址、电话、支付凭据、令牌或密钥；对方读取已开放的完整发货资料形成访问审计。
- API 的只读订单视图按访问者投影字段，不能先返回全量资料再由前端隐藏。
- 写命令及通用幂等响应只包含无完整地址／电话的订单摘要；完整资料通过独立的授权 GET 获取，不能绕过加密要求把原始地址写进 IdempotencyRecord.response。临时付款参数同样不进入通用幂等结果或审计。

面交不收集快递地址，本阶段不额外开发地图、定位、聊天或约见系统。

## 支付义务、可信事件与外部副作用

订单为双方各建立一份保证金付款义务；非零差价只为确认方案中指定付款方建立一份差价义务，受益人从订单另一方推导。客户端不提交金额、币种、付款身份或收款人，服务端从不可变快照计算。零差价不创建零金额支付单。本阶段服务费为零，不创建服务费付款。

每个 `(orderId, party, purpose)` 有唯一逻辑付款意图、唯一业务编号和不可变金额。网络失败或结果未知时复用原编号，查询合作方结果，不能新建另一张可能重复扣款的支付单。相同用户命令键同内容重放；同键不同内容冲突。

PaymentPort 至少定义创建付款、查询付款、关闭未完成付款、全额退款、查询退款和确认差价结算；LogisticsPort 定义核验／查询运单及可信物流事件输入。接口返回 pending／success／failure／unknown，不把超时当成明确失败。正式服务可采用不同保证金技术路径，但必须映射为本业务需要的“资金已满足、可返还、返还已确认”语义，不能猜测合作方能力。

数据库事务不能包含长时间第三方网络请求。业务事务先写状态、审计、幂等结果和持久化 outbox；worker 领取任务的短事务提交后再调用适配器，随后通过结果转换事务登记确认。领取任务与调用外部服务不能共享未释放的订单锁。worker 崩溃或收到超时后，按唯一业务编号查询／重试同一逻辑操作。

支付通知或 worker 确认结果须核验：可信来源、事件 ID、支付业务编号、外部交易号、订单、付款义务、金额、币种及事件类型。模拟签名规则只能用于模拟适配器，不能充当真实服务的验签实现。

- `(provider, eventId)` 唯一去重；不同事件 ID 重复报告同一外部成功交易，也不能重复记账或发货放行。
- 不可变资金事件记录和成功／失败状态、审计在同一事务提交。金额不匹配、错误币种或未知业务号不能完成任何付款义务；可信但无法关联的通知留作核对记录，不丢弃异常证据。
- 退款绑定原付款及唯一退款业务号，只允许本阶段已授权的全额退款；取消退款和完成后保证金返还不得对同一保证金重复执行。
- 外部已成功但本地审计事务失败时，不谎称外部资金已回滚。通知不确认成功／worker 保留待核对状态，后续用同业务编号重试登记。
- 晚到付款成功不得复活 CANCEL_PENDING、CANCELLED 或 ON_HOLD 订单；记录可信成功并进入退款或异常核对，不重新放行发货。
- 不提供运营任意金额退款、手动标记支付成功、保证金罚扣或通用余额接口。

### 测试适配器的隔离

显式 PAYMENT_PROVIDER=simulated／LOGISTICS_PROVIDER=simulated 只允许 development 或 test，订单响应带 simulation 标识，页面突出显示“测试支付／测试物流，不产生真实资金或寄递”。生产启动选择模拟服务立即失败。

测试支付完成只允许已认证 CUSTOMER 对自己所属订单、自己付款义务执行，不允许传入成功金额或其他参与人。模拟完成事件必须通过与正式接入共用的可信事件处理和审计路径，不能直接调用 Prisma 改订单状态。

测试物流驱动只作用于当前用户自己的出件，使用有序的模拟事件并走相同事件处理；不得改变别人的发货记录。用于 API 集成测试的注入适配器和时钟，以及浏览器测试专用驱动，都必须显式受环境和 provider 双重限制。测试驱动路由在正式配置中不注册。

## 发货、物流和面交

COURIER 模式每方只能为自己的整侧物品提交一个运单；服务端绑定包裹包含的全部物品和对应收货资料，禁止漏件、替换参与方或选择别人订单的地址。规范化 carrier／trackingNumber 并验证格式；同一承运人运单号不能用于不同发货任务。

提交运单只是“已登记”，不是“已发货”，必须经适配器可信揽收确认；两边均可信揽收才进入 IN_TRANSIT。当前数据格式校验不冒充真实揽收验证。已提交运单即视为可能已经交给承运人，不再允许通过取消释放物品；无效、重复或无揽收记录形成明确错误／异常状态。

物流事件不可变，重复和乱序通知保留去重记录，不把已签收进度倒退为运输中。事件时间使用合作方记录但期限裁决以服务端已确认状态和规则为准；提前验收需要自己的来件已经可信签收，客户端自报签收时间无效。异常状态只记录后续可信物流／资金事实，不自动恢复订单。

IN_PERSON 模式不允许填写运单，不调用物流适配器。双方分别确认已经交出自己一侧全部物品；双方确认后形成面交交接记录并分别进入来件验收。单方交接记录不能代替对方确认，产生交接记录后取消保护生效。第三阶段不使用验证码来替代另一用户的登录和显式确认。

## 取消、到期、异议与结算

### 无交接的取消

用户提出取消后，记录取消请求和理由；对方明确同意，且无人提交运单或面交交接记录，才进入 CANCEL_PENDING。拒绝、撤回和同意均需版本、幂等和审计。存在有效待回应取消请求时，禁止发货、交接和开始结算；原截止时间继续运行，不能靠反复申请无限续期。

同一订单同时最多一份待回应取消请求；请求方只能撤回自己的尚未同意请求，对方只能同意或拒绝。回应／撤回明确携带 cancellationId，核验其仍是当前未决请求及订单 expectedVersion，不能回应历史请求。重复提出不能延长原期限或创建第二份未决请求。

资料准备或支付逾期通过共同转换服务自动进入 CANCEL_PENDING，不需要另一方同意。所有请求均重新校验期限，定时任务延迟不能放行逾期付款或发货。

进入 CANCEL_PENDING 后停止新付款／履约命令，关闭所有已创建但结果未定的支付意图，核对结果并全额退还已成功保证金／差价。只有全部意图明确关闭或成功已退款，且无交接记录，才转 CANCELLED 并释放物品；结果未知时保留占用并显示“资金核对中”。没有任何支付意图的资料超时取消可在同一事务直接完成。

取消决定后晚到成功必须补做退款，不复活订单、不重复退款。若出现与已确认关闭／退款事实矛盾的可信外部结果，记录资金异常待处理；不得悄悄重新锁定已被其他业务占用的物品。

### 已有交接或验收异议

已有运单登记或面交交接后不能执行安全取消流程。发货逾期、可信物流异常、验收逾期、任一方明确报告验收异议进入 ON_HOLD，禁止自动结算和解锁。异议命令仅记录原因和冻结履约，不实现第四阶段的证据、责任认定或退货方案。

### 正常完成

双方面交／签收成立、各自确认验收且无异议、取消请求或到期期限冲突后，事务内进入 SETTLING、写审计并产生必要 outbox：差价结算给约定受益人及双方保证金返还。零差价无需差价结算任务。

全部必要任务经可信确认后才进入 COMPLETED，同时下架原物品并释放订单占用。任一任务结果未知或失败，显示结算待核对，不显示完成；再次执行复用原外部业务编号，不能重复支付受益人或返还保证金。不可解决的矛盾进入 ON_HOLD，第三阶段运营只读，不替运营默认决定资金去向。

worker 在领取和外部调用前核验任务仍与订单当前授权阶段相符；异常锁定后不得投递新的结算命令。已经发出的外部请求不能靠改数据库撤回，必须保存其在途义务、接收可信结果并核对，不能将其当作未执行再创建新业务号。正常终态不因重复或旧事件倒退；终态出现矛盾事实时额外记录异常待办，而非悄悄修改既有完成／取消历史或覆盖已释放物品的新占用。

## 锁顺序、版本与审计

全局顺序为：需要时先提案、再订单、再按 ID 排序的物品／占用、再资金及其他关联记录。订单常规命令只锁订单及必要下游记录，不反向锁来源提案。回调先按不可变关联信息解析 orderId，再锁订单并重读义务；不得先持有支付行锁再反向锁订单。

其他提案遇到订单占用立即返回 ITEM_UNAVAILABLE，不持有自己提案锁后再尝试锁另一订单。原提案到期／取消在释放租约前使用相同物品锁顺序，并只处理提案所有者的占用。排序和锁后期限复核必须覆盖所有涉及占用的转换。

审计覆盖提案转换、建单、资料更改／必要资料访问、付款发起／可信确认、退款、结算、运单登记／可信物流转换、面交交接、验收、取消请求／决定、到期与异常锁定。系统 actor 为 null，用户命令记录真实 CUSTOMER。所有审计不含完整个人资料和敏感接入数据。

审计失败必须回滚同事务的业务状态、物品修改、占用、资金记录、任务和幂等响应；对于已经发生的外部副作用，采用可重试核对而不是宣称数据库事务能撤销它。事件、资金确认、订单条款快照及审计采用数据库不可变保护，不提供修改／删除历史接口。

## 数据模型边界

实施计划应明确以下持久化模型、索引、约束和增量迁移：

- Order：唯一来源 proposalId，双方身份、总体状态、version、规则与条款快照、各期限、异常原因、simulation 标识。
- OrderItemSnapshot：完整确认版本物品内容、原所有者、归属方向和展示顺序；与来源版本对应且不可修改。
- OrderPartyProgress：每方的资料、资金、去件／来件和验收进度；订单与参与侧唯一，身份从订单推导。
- OrderAddress：加密资料与版本，按上述公开条件读取，冻结后不可更改。
- PaymentIntent：唯一订单／参与侧／用途、固定金额／币种、唯一业务号、状态和外部标识。
- IntegrationEvent：provider／eventId 唯一，可信通知摘要、去重与核对状态；原事件正文的敏感内容不进入通用审计。
- FinancialEntry：不可变付款、全额退款、保证金返还及差价结算确认记录，以义务和外部交易号防重。
- Shipment、ShipmentEvent：每方唯一发货任务、运单跨任务唯一、不可变可信物流事件和独立状态。
- OrderCancellation：请求方、理由、回应、版本和结果，不允许删除既有取消历史。
- OutboxCommand：唯一业务操作号、任务类型、领取租约、重试／核对状态和最后错误；不能只用内存 timer 表示外部待执行义务。
- ItemReservation：互斥的提案／订单所有者；现有主键和历史租约完整保留。
- Proposal：新增 CONVERTED 及关联订单视图；既有不可变报价、幂等和审计保留。

CHECK 和唯一约束额外保护金额非负整数、双方不同、占用所有者互斥、来源订单唯一、付款义务唯一、运单与外部操作唯一。服务端负责完整集合、身份、状态和期限的跨模型验证。

## API 与共享契约

共享包增加订单总体／双方状态、资金／运单／异常视图、命令 schema、错误码和 UTC 期限字段。金额和参与身份不由不可信调用方覆盖；所有请求拒绝未知字段。

| 接口 | 责任 |
| --- | --- |
| POST /api/proposals/:id/order | 参与者原子转换，校验提案 expectedVersion |
| GET /api/me/orders | 当前用户订单，按状态筛选和稳定游标分页，默认 20 条 |
| GET /api/orders/:id | 参与者视图，权限投影双方资料和资金信息 |
| GET /api/orders/:id/shipping-address | 自己收货资料或资金条件满足后自己的去件所需对方资料；对方资料访问审计 |
| POST /api/orders/:id/address | 当前用户自己的快递收货资料 |
| POST /api/orders/:id/payments | 当前用户发起自己的保证金或必要差价付款，仅传 purpose |
| GET /api/orders/:id/payments/:intentId/checkout | 付款义务本人授权获取当前有效付款参数，不返回他人付款凭据 |
| POST /api/orders/:id/shipments | 当前用户自己的快递运单 |
| POST /api/orders/:id/handover | 当前用户自己的面交交接确认 |
| POST /api/orders/:id/acceptance | 当前用户对自己的来件验收 |
| POST /api/orders/:id/issue | 当前用户报告验收异议，进入待处理 |
| POST /api/orders/:id/cancellation | 当前用户提出取消 |
| POST /api/orders/:id/cancellation/respond | 对方同意或拒绝当前取消请求 |
| POST /api/orders/:id/cancellation/withdraw | 请求方撤回尚未同意的请求 |
| GET /api/admin/orders | 三种运营角色只读分页查询，含异常筛选 |
| GET /api/admin/orders/:id | 三种运营角色只读、脱敏详情 |

所有用户 POST 必须提供 Idempotency-Key；建单使用提案 expectedVersion，其他命令使用订单 expectedVersion。成功命令返回无完整地址、电话和付款凭据的授权摘要；付款发起返回关联 PaymentIntent 标识与 pending 状态，不伪装同步成功。付款参数通过独立授权 GET 获取，参数未生成时返回明确 pending，接口不得另建付款意图或重复扣款。幂等响应按 actor／command／key 保存，内容哈希包括资源 ID 和完整规范化请求。

正式支付／物流回调接口只在相应真实适配器存在时注册，具体路径和验签字段在选择合作方后按官方文档确定。本阶段注册仅模拟配置下的受控测试驱动接口，不能开放无验签的“通用支付成功”路由。

读接口必要的期限检查先核验参与权限，再调用共享到期转换；运营读取不触发变更，显示持久化状态、期限和异常。第三阶段运营只读订单、脱敏资金与物流状态，不能代用户命令或执行资金处置。

错误包括 AUTH_REQUIRED、FORBIDDEN、VALIDATION_FAILED、ORDER_NOT_FOUND、ORDER_VERSION_CONFLICT、ORDER_INVALID_STATE、ORDER_EXPIRED、ORDER_DETAILS_REQUIRED、ORDER_PAYMENT_NOT_READY、ORDER_FULFILLMENT_STARTED、ORDER_CANCELLATION_PENDING、ORDER_ON_HOLD、ORDER_ALREADY_EXISTS、PROPOSAL_ALREADY_CONVERTED、ITEM_UNAVAILABLE、IDEMPOTENCY_CONFLICT、TRACKING_NUMBER_IN_USE、INTEGRATION_EVENT_INVALID、INTEGRATION_UNAVAILABLE。不存在／非参与者统一 404；身份或职责不符 403；版本、状态、期限、占用竞争 409；未配置接入 503。异常响应统一现有 ApiErrorBody 和 requestId。

## 前端交付

Taro 提案详情增加“生成交换订单”及转换后订单入口，“我的物品／投物箱”可进入我的订单。订单页分开展示双方物品、差价方向、保证金、去件／来件、时间和测试标识。只为当前用户的合法动作提供资料、付款、运单／面交、验收、异议和取消控制。金额展示可格式化为元，但提交和契约始终整数分。

按钮禁用不是权限边界。网络结果未知时保留原逻辑幂等键；版本冲突刷新并要求重新确认。异步旧读取不能覆盖较新的命令结果。支付页面“已点击付款”不等于资金成功；订单刷新只依据 API 可信状态。异常和资金核对中应显示明确原因，不提供绕过步骤的完成按钮。

运营工作台增加桌面表格、手机卡片的订单列表和只读详情，展示双方进度、脱敏资料、资金任务和异常待办。长标识正常换行，390px 无横向溢出。保留原审核及提案页面；无代付、代验收、改状态、直接退款按钮或隐藏管理路由。

## 测试与验收

每个实现任务先添加失败测试并确认预期失败，再最小实现、通过测试、独立审查和单独提交。详细任务顺序与提交信息在后续实施计划确定；不得并行修改相互依赖的模块。

必须覆盖：

- 两名参与者与第三人、各运营角色及混合 CUSTOMER／运营角色的服务端资源权限；地址与资金隐私不泄漏，包括通用幂等记录和审计。
- 两方同时建单、转换与取消／到期扫描竞争，只能成功一个决策；全部 2～6 件原子交接，缺失或错误租约整笔失败。
- 转换后超过原 72 小时仍不可投；原提案取消／到期不得释放订单占用；完成物品下架，安全取消恢复可投。
- 同键同内容、不同内容、不同资源、网络重试及双人重复转换；不重复订单、审计、付款或外部任务。
- 资料、资金、运单、验收、到期和最终物品修改的审计失败回滚；外部成功／本地失败后可核对恢复且不重复执行。
- 保证金双方独立、差价方向和金额完全取自快照；错误签名／金额／币种／业务号不放行。
- 重复、乱序、晚到支付／退款／物流事件；不同事件号报告同一成功交易不得重复记账。
- worker 在调用前、调用成功后、结果提交前崩溃的恢复；unknown 不能重复扣款、返还或结算。
- 资金未齐不能发货；一方不能提交另一方运单；重复运单、未揽收、错误模式、漏件和提前验收被拒绝。
- 取消与付款、发货、面交、验收竞争；已有交接不能释放；取消请求未决不能发货或结算。
- 资料／支付到期、共同发货到期、每方验收到期；请求与定时任务一致，拒绝过期操作。
- 快递多物换一物及面交闭环；异议／物流异常不结算；零差价不生成差价支付或结算任务。
- 模拟服务和驱动在生产无法启用；生产缺少服务／加密配置明确拒绝；UI 不把模拟结果呈现为真实。

Playwright 保留前两阶段三条流程，并新增两个隔离客户会话的快递订单闭环：确认方案 → 建单 → 各填自己的测试地址 → 各缴测试保证金和约定差价 → 双方运单及可信模拟物流 → 双方验收 → 测试结算／保证金返还 → 原物品不再可投。另测未发货取消退款释放、面交闭环和 390px 运营订单只读权限。浏览器可使用受控测试驱动推进外部事件，但不得 mock 业务后端或直接改数据库冒充用户步骤。

完成前分别运行 `npm run lint`、`npm run typecheck`、`npm test`、`npm run build`、`npm run verify`、`npm run e2e`。CI 使用 PostgreSQL 17，不替换成 SQLite。须证明新迁移可从前两阶段数据增量升级，并保留全部原有审核与协商测试。
