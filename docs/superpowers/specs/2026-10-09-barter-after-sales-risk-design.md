# 第四阶段：售后与风险控制设计

日期：2026-10-09。状态：用户已确认设计；实施计划须单独审阅后执行。

## 1. 目标、基线与已确认边界

前三阶段已建立发布审核、结构化协商、双向订单及受控模拟履约。本阶段让交易双方处理履约争议，让运营人员有可追溯的证据、退货、补偿和风控工作流，而不是直接修改数据库或冒充用户。

开发基线为 `main` 的 `f6d459f851fe8af448353215b892b7002896cd0e`，第三阶段 PR #3 已合并。设计分支为 `codex/phase4-after-sales-risk`。实施开始前重新确认基线和工作区；不改写历史提交或已应用迁移。

用户已确认继续使用受控模拟资金与物流：不发起真实扣款、退款、补偿或物流业务。继续使用现有 npm workspaces、TypeScript、Taro 4/React、React/Vite/Ant Design、NestJS、PostgreSQL 17、Prisma 7、Zod，以及仓库现有 Vitest/Supertest/Testing Library/Playwright。保留已有生产适配器不可用时明确拒绝的行为，不用模拟器或本地存储冒充生产接入。

纳入：售后申请与处理记录、私有图片证据、双方退回原物、独立补偿约定、暂停订单的受控恢复、异常运单、举报、单个账号交易冻结及单个物品下架、运营重新验证及资金处置审批。

不纳入：聊天、真实支付物流、平台钱包、自动罚扣保证金、部分退款、批量封禁/下架、角色或费用配置、自营回收、仓储验货、会员、直播、估价、独立运营小程序。第五阶段负责正式试运营规则与上线门槛。本阶段规则是显式版本化的模拟验收规则，不代表真实交易法律承诺。

## 2. 方案选择

推荐“工单驱动的独立售后编排”：工单关联订单快照，保存不可修改的方案与裁决，调用订单、资金和物流模块公开的命令接口。原始履约事实保留，新增事实表达退货与补偿。可以独立测试每个模块，并复用已有 outbox 与对账机制。

替代一是给后台增加通用状态修改接口。代码较少，但无法可靠约束退款、占用和双向退货的条件，不采用。替代二是自动判责与自动赔付。需要尚不存在的业务规则、真实供应商能力和证据判断机制，本阶段不采用。

以下时限、金额上限及审批规则已随本设计获得用户确认，作为实施依据。

## 3. 工单、状态与时限

### 3.1 创建与访问

只有订单参与方的纯 CUSTOMER 会话能申请售后。第三人访问返回 404；运营通过独立管理接口访问，混合用户/运营身份不能使用客户命令。创建必须携带 Idempotency-Key 和 expectedOrderVersion，先锁订单，再判断资格。

尚未关闭的订单在发生争议、物流异常、履约超时或资金异常时可以申请。COMPLETED 订单允许在完成时间后 7 天内申请；必须新增持久化 completedAt，并从既有完成审计迁移确定历史值，无法确定的旧记录不猜测日期，进入人工核验。CANCELLED 订单只允许针对退款异常申请资金工单，不能重新发货或恢复交易。已有退款/结算中的订单可以申请，但不得声称已发出的外部资金指令被数据库回滚撤销。

每个订单最多一份未关闭工单，以 PostgreSQL 部分唯一索引保证。双方在同一工单分别描述诉求与补充证据；不各建一份竞争工单。已关闭工单只能创建后续工单，不能改写原裁决；同一根争议及同一已执行义务不能重复处置。

首次创建工单、冻结非终态订单、递增订单版本、记录原状态及审计在同一事务完成。原订单为 ON_HOLD 时保留首次暂停原因和未完成义务，同时追加新的风险/工单原因，不覆盖旧原因。COMPLETED/CANCELLED 不倒退成 ON_HOLD，工单独立存在。

### 3.2 工单状态

`OPEN` → `AWAITING_RESPONSE` → `UNDER_REVIEW` → `AWAITING_AGREEMENT` → `EXECUTING` → `RESOLVED`。

OPEN 表示申请已受理；运营可要求指定一方补证，进入 AWAITING_RESPONSE；收到答复或期限届满进入 UNDER_REVIEW。运营提出方案进入 AWAITING_AGREEMENT；双方同意，或有权限的裁决完成所需审批后进入 EXECUTING。所有退货、资金与订单收尾义务均已明确完成才进入 RESOLVED。

`REJECTED` 与 `WITHDRAWN` 是不执行方案的关闭结果。撤回需双方确认；若已有风险标记、外部资金执行、退货登记或待处理事实，只能提交撤回请求，不能自动关闭或恢复订单。驳回/撤回不等于解除订单的其他暂停原因。

补证与方案回应期限各为 72 小时；未回复仅产生逾期待办并转人工审核，不默认同意、判责、退款或释放物品。拒绝方案返回 UNDER_REVIEW，理由作为不可修改的处理记录保存。截止边界使用服务端 UTC 时间，`now >= deadline` 即逾期；定时任务和请求检查共享转换服务。

## 4. 证据与隐私

证据是工单/举报范围内的私有附件，不复用公开 ItemImage URL。支持 JPEG、PNG、WebP，每张不超过 8 MiB，每条证据说明可附 1～9 张，一份工单双方各最多 30 张。说明长度 1～2000 字。视频、文档和自由链接不在本阶段上传范围；可用图片提交包装、开箱、运单等证明。

文件必须校验真实格式、可解码性、最长边不超过 8192 像素且总像素不超过 4000 万，拒绝伪 MIME、SVG、路径穿越和畸形图片。保留原始文件及摘要用于核验，展示使用去除 EXIF 的安全派生图片；两者都只经授权接口读取，不对外发布永久 URL。记录上传者、实体 ID、摘要、字节数、格式、上传时间与说明，禁止替换已提交文件或修改说明。纠正通过新证据和补充记录完成。举报附件同样每次最多 9 张、每名举报者每份举报最多 30 张。

工单证据由双方及具有售后处理权限的运营读取；举报证据仅举报者与审核风控/超级管理员读取，不自动向被举报者泄露举报者身份或附件。下载逐次鉴权，响应不缓存，原始证据下载另写访问审计。泛化列表、幂等响应与状态审计不包含文件内容、地址、密码或访问凭证。

开发/测试可使用独立私有本地目录；生产未配置私有对象存储适配器时明确不可用，不能回退到公开物品目录。先存对象再提交元数据；事务失败的孤立对象由有归属、有限范围的清理任务回收，不删除已引用证据。

Task4 接口澄清（2026-10-12）：`POST /api/after-sales/:id/evidence` 使用 multipart，重复 `files` 字段上传图片，文本字段仅为 `description`、`expectedCaseVersion`、`expectedOrderVersion`；不接受预上传 `imageIds` 或 URL。共享举报追加元数据仅含 `description/expectedVersion`，举报路由仍由 Task7 接通。幂等摘要包含服务端从实际原件计算的 SHA-256 及文件次序。举报追加返回严格 `{resourceId, version}`，富视图由独立鉴权查询提供。工单详情的 `evidence` 仅提供脱敏元数据；运营投影不含上传者 ID。读取 `GET /api/evidence/:id/content?variant=preview|original` 每次验证参与方或绑定运营会话，成功响应使用 `Cache-Control: no-store`，原件访问审计提交后才返回字节。

## 5. 不可修改的方案与裁决

运营客服或超级管理员可以提出售后方案。方案版本保存作者、原因、关联证据、商品快照 ID、责任结论、运费承担、补偿方向/金额、退款与结算目标及规则版本。方案不可更新/删除；新版本使旧版本所有确认与批准失效。

方案类型为 `CONTINUE_EXCHANGE`、`RETURN_ORIGINALS`、`KEEP_WITH_COMPENSATION`、`CANCEL_BEFORE_HANDOVER`、`FUNDS_ONLY`。每个方案必须明确每一笔原保证金/差价的去向、退货双方义务，以及订单收尾结果。不能提交“以后由后台决定”的资金状态。

CONTINUE_EXCHANGE 的执行完成条件是风险解除、期限与状态安全恢复，此时工单即可结案，后续正常履约仍由订单负责。RETURN_ORIGINALS/CANCEL_BEFORE_HANDOVER 的非终态订单在履行归还及退款义务后进入 CANCELLED；KEEP_WITH_COMPENSATION 在双方各自明确确认已收到并保留全部物品、补偿及原正常结算完成后进入 COMPLETED，方案同意不能代替物品验收。FUNDS_ONLY 不修改已终结订单状态。终态订单上的任何方案只记录售后结果，不改写历史终态。

未进入 EXECUTING 前可以提出新版本；开始执行后不得换方案绕过在途资金或退货，必须先完成对账、关闭可安全关闭的义务并记录明确终止结果，才允许提交后续方案。每项原差价回转、退款与补偿使用根争议及原支付引用去重，不能通过新建工单重复回转同一笔原差价。

双方只能确认当前方案，不能以用户身份改变另一方证据或代对方确认。双方同意是事实记录，不是管理员审批。运营裁决允许在证据不足、拒绝或逾期后确定处理方向，但不能伪造用户同意、收货或扣款授权。涉及资金的方案，执行前仍需要第 9 节资金审批；所有计划资金动作由服务端推导，客户端不能直接提交任意 businessNo 或账户。

## 6. 退货与占用

一份订单始终保留发起方 1～5 件、接收方 1 件。退货按每件 OrderItemSnapshot 建立归还义务，实际持有人退给快照原物主。未交付的物品不要求虚构反向运单。仅登记了运单也不能直接当作“从未发货”：必须完成模拟物流关闭/拦截核验，或建立相应退回义务。

快递退货建立独立 ReturnShipment，支持同一方向多件合包，保存覆盖的快照 ID；不能把退货运单写回原 Shipment。面交退回由交出方登记、原物主独立确认，不允许运营代确认。快递物流签收是证据，最终接收确认由原物主完成；拒绝/逾期进入人工核验，不能自动视为完好返还。

双方在方案执行后 72 小时内登记退货；揽收后 7 天未送达或物流异常进入人工处理；收到后 72 小时内确认或提出异议。全部物品归还、拦截关闭或经裁决明确无法归还，并完成规定资金动作后才能关闭工单。资金 UNKNOWN 或未明确归属时保留非终态订单占用，不以超时释放。

非终态订单沿用原订单占用，期间不能再次投物。成功终止交换后释放占用，但曾交付或存在质量争议的原物品设为 INACTIVE；原物主重新编辑提交审核后才能上架，不自动恢复 ACTIVE。未交付且无物品风险的安全取消才允许恢复原上架状态。

对 COMPLETED 订单，原占用早已释放，不重新占用原 Item ID、不抢占后续交易、不覆盖原订单完成事实。退货依独立归还义务跟踪，返回原物后需新建发布并审核。系统不宣称能够识别或锁定用户另行发布的同一实物。发现关联交易风险时运营通过独立风控命令处置，不能在售后关闭时批量回溯改订单。

## 7. 原款退款与独立补偿

所有金额为整数分，币种固定 CNY，金额/方向均在不可修改方案中明确。零补偿必须 payer=NONE。每个方向额外补偿上限 20000 分，运费补偿上限 20000 分；已结算原差价的回转不超过订单原差价。为避免复杂循环，本阶段每份方案只允许一笔净补偿，单笔不超过 60000 分（原差价回转、额外补偿、运费三项逐项校验），正负项净额化后明确唯一付款方与收款方，禁止浮点或用负数表示金额。

原 PaymentIntent、FinancialEntry 和订单规则快照不可改价。未结算的原差价可以整笔退给原付款方；继续交换则按原条款结算。保证金只整笔退回原付款方，不罚扣、不用于运营自由支配或代付补偿。已成功结算的原差价不能伪装成原支付退款，需在新方案中记为补偿回转。

新增独立 CompensationObligation、CompensationPayment 与不可修改资金事实。付款者确认该义务后主动进入受控模拟支付；裁决可以记录其应付责任，不能凭裁决直接扣款。补偿到账与转付收款方是不同事实；转付未知持续对账，不能再收第二次。补偿支付期限为执行方案后 72 小时，未支付超时转运营待办，不默认从保证金扣除。取消尚未执行补偿方案时关闭支付；已收款、未转付则原路整笔退回；已转付时不能撤销历史，需要新的经审批方案。CONTINUE_EXCHANGE 不提前退还履约所需保证金，仍遵守原订单完成或安全取消条件。

扩展模拟资金端口，分别表达补偿收款、原路退款、转付及原业务号查询；原款整笔退款仍复用原退款业务号。采用 outbox 先记录义务与审计，再在事务外执行，之后按可信回调/查询事实落账。UNKNOWN 查询原 businessNo，不换号重试。不把数据库回滚描述为外部退款回滚。

每笔资金义务必须有唯一来源方案/执行步骤、单一终态及金额守恒约束。已退款原款不能再结算，已结算原款不能再退款；补偿已转付不能再原路退款。整笔退款总额不超过对应实际收款额；补偿转付不超过新补偿到账金额。外部事实与计划冲突时保留原事实、审计与异常待办，不自动解冻、改终态或释放占用。

## 8. 暂停恢复、举报与违规账号

### 8.1 有边界的恢复

不提供任意 `setStatus`。CONTINUE_EXCHANGE 方案经过确认和必要审批后，依据最新可信资金、物流、验收事实重新计算允许的下一状态，而不是盲目恢复 holdPreviousStatus。仍有活跃风险、资金未知或其他工单阻塞则拒绝恢复。

运营最多延长同一订单每类详情、支付、发货或验收期限一次，延长 72 小时，起点是批准时服务端时间；记录原截止、新截止、原因及受影响方。不能修改已完成事实，不能延长一方期限就默认另一方同意改变商品或价格。待执行方案、未查询的原资金指令先对账后恢复。恢复与期限修改都校验工单及订单版本。

### 8.2 举报与单项处置

客户可举报公开物品、订单关联运单或违规交易行为。订单/运单举报仅参与方可提交，不泄露非参与订单存在性；公开物品举报按已有公开可见性校验。保存结构化原因、说明及私有证据。举报身份不在公开或被举报人接口出现。同键重试返回原结果；同一人、同一目标、同类原因存在开放举报时返回已有举报，新增证据走追加命令。

举报状态为 OPEN、INVESTIGATING、ACTIONED、DISMISSED。审核风控/超级管理员可认领、补证、记录结论，并通过独立命令下架单个物品、交易冻结单个账号或暂停单个关联订单。处置与举报关联，但不能用关闭举报自动解除限制。客服可处理普通售后，不能冻结账号或关闭风控举报。

新增交易限制状态与原因、版本及解除审计，不直接复用 User.disabledAt。交易冻结阻止新的发布/提交、提案创建/修改/接受以及转订单；保留登录、自有记录、售后举证、必要退货及现有退款读取。冻结者的 ACTIVE 物品在公开发现接口隐藏并不可被新提案接受；不批量改写每件状态，解冻后仍独立保留已下架物品状态。原未确认提案在请求时核验双方限制，不能绕过冻结。

冻结和提案接受/转订单共用用户限制行锁，参与用户按 ID 排序在订单/提案资源锁前取得，防止校验后冻结的竞态。已有订单不批量自动取消；需要暂停时逐单显式操作。单项下架保留订单快照和占用，用户不能通过编辑重新上架；解禁仍需审核流程。

异常运单可信回调保留事实、暂停相应非终态订单并建立去重风险待办。终态订单仅追加异常事实/待办，不回退终态。运营可要求举证、查询原运单或批准具体退货/恢复方案，不可直接把 EXCEPTION 改成 DELIVERED。认定虚假运单需理由和证据，不只依据超时。

## 9. 角色、设备会话与高风险审批

CUSTOMER：自己的工单、证据、方案确认、补偿支付和退货；没有运营权限。

OPERATIONS：脱敏工单/订单查询、补证、处理记录和方案起草；不能独立批准资金执行、冻结账号或代替用户确认。

REVIEWER：脱敏风险查询、举报处理、单项下架、交易冻结与暂停订单；不能执行资金处置或修改用户发布内容。

SUPER_ADMIN：以上管理权限，批准受控恢复与资金方案；不能越过资金守恒、可信事实、版本校验、二次验证及审批要求。

普通移动运营会话允许只读、单项下架/交易冻结、暂停及补证等紧急止损。资金方案批准与执行仅接受服务端已登记的 DESKTOP_PRIVILEGED 会话，且操作前重新验证管理员密码。不能通过 viewport、User-Agent、客户端传来的 deviceKind 或单独隐藏按钮授予权限。

解除交易冻结属于恢复而非移动紧急止损，要求 DESKTOP_PRIVILEGED，角色限 REVIEWER 或 SUPER_ADMIN。恢复订单另要求 SUPER_ADMIN；具备设备能力不会扩大角色权限。

单项冻结/解除、下架、暂停/恢复以及所有资金批准/执行均要求动作级二次验证和原因；移动会话只能申请其允许止损动作的 grant，不能申请桌面专属动作。普通补证/处理记录无需重复输入密码，但仍要求有效会话、版本、幂等及审计。

新增 OperatorSession、OperatorDevice 与 ActionGrant。设备登记请求只生成待批准记录，不能自授桌面权限；部署管理员通过受控服务器 CLI 首次批准桌面设备，后续超级管理员通过已有受信桌面会话批准/撤销。审批不可由请求者自批；首次启动仅使用服务器运维通道，不开匿名网页后门。浏览器绑定不可由客户端随意选择的随机设备凭据，服务端同时校验有效会话、已批准设备和当前数据库角色。撤销立即失效，移动会话有效期 15 分钟，桌面会话不超过 30 分钟。

这里的“桌面”是经运维批准的高权限设备会话能力，不是物理设备识别；浏览器无法仅凭 HTTP 信息证明电脑型号。设备注册不得被描述为硬件认证或 MFA。二次密码验证证明操作时重新验证，不能声称拥有真实多因素接入。真实上线若要求硬件/多因素保证，属于第五阶段安全门槛，需接入实际认证能力。

ActionGrant 绑定 actor、session、device、action、资源 ID、完整 `expectedVersions` 与 `requestHash`（原文的 expectedVersion 是所涉资源版本的统称），5 分钟有效且一次性。消费端从业务输入在服务端规范化计算摘要，不把客户端提交的 hash 当作业务授权校验。成功敏感命令在同一事务消费 grant 并写审计；业务冲突回滚时不伪造已执行。相同幂等键的成功重试先核验当前身份/设备权限，再返回脱敏原结果，不再次消费 grant 或执行资金动作。改内容、换资源、重用 grant 均拒绝。

实现澄清（2026-10-09）：新 POST `/api/admin/security/login` 使用共享严格契约承载绑定设备的 sid 会话，登录响应不返回设备秘密。原无 sid 的低风险登录/查询/审核保持兼容，但不能取得第四阶段敏感授权。尚未发布的 grant 签发 DTO 直接采用完整版本/摘要字段，不增加旧单版本签发入口。

会话列表与自行撤销限当前运营人员本人；跨账号的单会话管理不在本阶段扩展。受信超级管理员撤销设备会立即使该设备绑定的会话与授权失效。设备及会话撤销使用持久化资源版本并审计；已被撤销的当前会话不得通过幂等回放取得旧敏感结果。

资金方案实行两名不同 SUPER_ADMIN 的审批；起草者不能审批自己的方案，同一人不能充当两名审批者。模拟测试提供两名独立超级管理员，真实部署人数不足时资金处置明确保持待审批，不用开发环境开关偷偷取消审批。参与客户同意与管理员审批分开保存；任一方案变更使全部旧审批失效。每次实际执行仍验证当前方案、版本、角色和风险状态。一次审批不授予任意退款权限。

## 10. 模块、持久化与契约

模块划分为 after-sales（工单/方案/裁决）、evidence（私有证据）、returns（归还义务与物流）、compensation（独立资金义务）、risk（举报/限制/待办）、operator-security（会话/设备/二次验证/审批）。订单与现有资金、物流模块提供显式领域服务，禁止跨模块直接调用内部状态更新方法。

主要新增模型：AfterSalesCase、CaseRecord、CaseEvidence、ResolutionVersion、ResolutionConsent、ResolutionApproval、ResolutionExecution、ReturnObligation、ReturnShipment、ReturnEvent、CompensationObligation、CompensationPayment、CompensationFinancialEntry、RiskReport、RiskRecord、TradingRestriction、RiskTask、OperatorSession、OperatorDevice、ActionGrant。方案、确认、审批、处理记录、资金事实和证据元数据通过数据库约束/触发器保持不可修改；进度和接收处理状态另存可变行。迁移保留现有数据，只向自有临时验证数据库应用，不擅自迁移保留的业务库。

共享 Zod 契约定义所有状态、严格写命令、脱敏查询视图、整数分、UTC ISO 8601 和错误码。用户端与管理端共用领域类型但用不同读写接口，运营响应不泄露用户地址、OpenID、支付凭证或举报者身份。

接口族：`/orders/:id/after-sales` 创建；`/after-sales` 自有列表与详情；工单 evidence/response/consents/return/compensation 命令；`/reports` 自有举报；`/admin/after-sales`、`/admin/reports`、`/admin/risk-tasks` 管理查询和专用命令；`/admin/security` 设备会话与 grant。私有文件读取使用独立鉴权接口。列表采用 `(createdAt,id)` 稳定游标，默认 20、最多 50。

所有用户/管理业务写命令要求 Idempotency-Key、资源 expectedVersion；创建使用关联订单版本，举报公开目标使用目标版本。登录及密码验证不是可缓存业务命令，凭证不得进入幂等存储。方案批准/执行同时携带 expectedCaseVersion、expectedOrderVersion、resolutionVersion，涉及用户限制或物品另带相应 expectedVersion。相同键同内容返回原结果，内容不同返回 409 IDEMPOTENCY_KEY_CONFLICT。敏感响应只缓存脱敏事实，不缓存文件、地址或短期授权。

主要错误：AFTER_SALES_NOT_ELIGIBLE、AFTER_SALES_ALREADY_OPEN、CASE_VERSION_CONFLICT、ORDER_VERSION_CONFLICT、RESOLUTION_VERSION_CONFLICT、EVIDENCE_LIMIT_EXCEEDED、RETURN_NOT_READY、FUNDS_UNRESOLVED、TRADING_FROZEN、RISK_BLOCKS_RESUME、REAUTH_REQUIRED、DESKTOP_SESSION_REQUIRED、APPROVAL_REQUIRED、GRANT_INVALID。并发/状态竞争返回 409，身份错误 401，权限错误 403，跨用户不存在性统一 404，输入错误 400，适配器不可用 503。

Task3 基础处理契约澄清（2026-10-12）：创建输入为 `expectedOrderVersion/reason/previousCaseId?`；后续工单通过不可修改 OPENED 记录关联前序关闭结果，服务端沿关联继承根争议，不能用导入记录的时间戳推断前序。历史 `completedAt` 缺失或前序关联有歧义时返回 409 `AFTER_SALES_NOT_ELIGIBLE`，错误 `details.manualVerificationRequired=true`。CANCELLED 的资格根据关联原支付、原退款及未知指令事实判定，不根据说明文本。

基础回应 `POST /api/after-sales/:id/response` 收 `expectedCaseVersion/expectedOrderVersion/description`；撤回请求 `/withdraw` 收两版本和 `reason`，另一方 `/withdraw/respond` 收两版本、不可修改的 `withdrawalRequestId`、`decision=AGREE|REJECT`，拒绝必须提供理由。关联 order/root 的活跃风险、明确暂停 blocker、待核验外部事实及未完成义务阻止关闭；用户交易冻结状态本身不自动成为任意订单的关闭 blocker。既有义务只读取各领域持久化完成标记与已确认资金事实，缺失或 UNKNOWN 转核验，不在基础关闭命令中伪造完成。

绑定会话的 OPERATIONS/SUPER_ADMIN 可通过 `POST /api/admin/after-sales/:id/request-evidence` 提交两版本、`side` 和 `reason`；普通工单 `/reject` 提交两版本与不可修改驳回理由。基础驳回不处置当前方案，客户拒绝实际方案仍属于后续方案契约。客户与管理详情增加脱敏 `records` 时间线，记录只包含 id、kind、actorKind、side、description 和 createdAt；管理列表、详情与命令响应使用独立显式投影，不随客户视图自动扩充。详情以同一数据库快照读取工单版本与记录。

## 11. 事务、并发与异步一致性

统一锁顺序：需要检查交易限制时先锁涉及用户限制行（按用户 ID 排序），再按第三阶段顺序锁来源提案（若需要）→订单→工单/当前方案→物品及占用（排序）→资金/退货/审批/授权记录。只访问工单的命令仍先定位并锁其订单，不出现工单→订单反向锁。冻结只操作限制行，不在同一事务遍历订单，避免形成反向锁。回调先由不可修改元数据找到订单，再按同一顺序加锁。

资源版本、状态、时限、风险、授权都在锁后重新检查。状态、审计、不可修改事实、幂等记录和 outbox 在同一 PostgreSQL 事务写入；审计失败全部回滚，不留下半份方案、半份占用或授权消费。外部调用在事务外；已有第三阶段 worker 能继续查询未知旧业务，售后不能用暂停阻止可信事实入账。

新增方案只冻结未来未执行指令，不声称撤销正在执行或已经成功的指令。执行前确认没有未知且冲突的旧资金指令；不存在竞态安全证据时保持待核验。重复回调、重复定时任务和并发批准均由唯一约束、版本与稳定业务号解决。终态事实冲突新增异常记录，不重写旧账。

## 12. 两端页面与验收

小程序订单详情增加售后入口、诉求与图片证据、双方处理时间线、方案比较及确认/拒绝、补偿模拟支付、快递退货/面交归还与收回确认。交易冻结提示解释哪些新交易被限制，同时保留售后入口。私有图片使用已鉴权读取，不复用公开图片组件的永久链接。

运营网页增加售后队列/详情、证据查看、结构化方案编辑、风险待办与举报、交易冻结及恢复、独立设备会话与资金审批页面。390px 可完成单项补证、查询、暂停和交易冻结；资金审批移动布局不开放，API 同时校验桌面能力。管理人员行为在时间线标为平台处理，不伪装成某个用户操作。

验收覆盖：跨用户/混合身份越权；冻结与接受提案竞态；证据私有访问及畸形图片；重复创建/确认/回调；双方同时修改/批准；审计失败回滚；新方案使旧确认/授权无效；客服不能执行资金；移动会话伪造 deviceKind 仍被拒；两名独立批准者及二次验证过期；双方多物退货、只交付一方、面交退回；未知退款/补偿保留占用；既有支付回调迟到；已完成订单售后不抢占新交易；逾期不自动确认；冻结用户仍能履行退货；恢复时风险未解除必须拒绝。

Playwright 至少演示两条跨端链路：双方交换出现争议→举证→运营提出退货→双方同意→桌面双人审批→双方退回原物→核验退款→结案；双方同意保留物品并补偿→审批→付款方模拟支付→原业务号核验转付→结案。另验证移动运营止损与资金拒绝、风险解除后受控恢复。

实施继续先失败测试再最小实现，按依赖顺序每任务使用新实现代理和新审查代理，分别检查需求符合度与代码质量，逐任务提交，最后做整分支独立审查。保留第三阶段的身份切换、私有信息、账目与数据库隔离回归，不作无关重构。

完成前分别执行 `npm run lint`、`npm run typecheck`、`npm test`、`npm run build`、`npm run verify`、`npm run e2e`，记录真实结果。测试/E2E 仅创建和销毁自身数据库，证明保留源库未修改；不使用 SQLite、数据库 reset 或强制删除。更新 README、AGENTS、实施记录和 CI。真实外部凭据欠缺不以假接入补齐，也不把模拟验收写成真实资金上线验收。
